## Context

当前 poems 表已保存标题、作者、朝代、词牌、正文 JSON 和标签 JSON；`PoemRepository` 只提供按 id、按朝代/类型列表和计数。产品要求 local-first，搜索不能依赖网络，也不能把用户输入发送给 LLM。首版数据规模从种子集到导入的完整诗库，适合使用 SQLite 的参数化 `LIKE` 查询，暂不引入新的 FTS 迁移。

## Goals / Non-Goals

**Goals:**

- 在已有 SQLite 数据上提供稳定的关键词查询。
- 在分类页通过标准搜索交互让用户输入即查，并可进入阅读页。
- 搜索覆盖用户最常用的元数据和诗文内容。
- 查询结果有上限、稳定排序，避免一次渲染过多记录。

**Non-Goals:**

- 不实现分词、拼音、模糊纠错或网络搜索。
- 不增加数据库表或迁移步骤。

## Decisions

### 1. 先使用参数化 LIKE，不新增 FTS 表

在 `title`、`author`、`rhythmic`、`paragraphsJson` 和 `tagsJson` 上执行包含匹配。Drift 会把模式作为变量绑定，输入中的 `%`、`_` 和反斜杠先转义，用户输入按字面意义搜索。这样无需升级现有 schema，也能覆盖中文短语和导入数据。

备选方案：新增 FTS5 虚拟表。FTS 更适合大规模全文检索，但需要维护 JSON 数组的索引同步、迁移和中文分词策略；首版数据量和需求不足以承担这些复杂度，后续可独立优化。

### 2. 在分类页使用 SearchDelegate

分类页 AppBar 增加搜索图标，打开 Flutter 原生 `showSearch`。`PoemSearchDelegate` 复用仓库接口，在 suggestions/results 阶段展示同一套本地结果列表；结果点击返回诗实体，由分类页导航到 `/poem/:id`。这样搜索页面有系统返回、清除、键盘提交和平台一致的体验。

### 3. 结果排序与限制

先按 `popularity DESC NULLS LAST`，再按 `id ASC` 稳定排序，限制默认 50 条。首版不展示复杂相关性分数；标题/作者命中与正文命中都可以通过结果标题和副标题识别。

### 4. 查询安全与空输入

去除首尾空白；空输入不访问数据库而展示提示。LIKE 模式中的 `\\`、`%`、`_` 被转义并指定 ESCAPE `\\`，不允许输入改变查询通配行为。查询为只读操作，不触碰收藏、注本或 LLM 配置。

## Risks / Trade-offs

- [LIKE 在完整导入库上可能比 FTS 慢] → 限制结果数量，保留稳定索引排序；若实测超过可接受时延，再单独引入 FTS 方案。
- [JSON 序列化字段会带有括号/引号] → 只做包含匹配，不把 JSON 格式暴露给用户；正文和标签文本仍可被命中。
- [搜索结果在输入过程中频繁请求] → 仅在非空查询触发，SearchDelegate 自带查询变更节奏；仓库调用为本地只读。
- [用户输入特殊符号] → 统一 LIKE 转义并增加 `%`/`_` 回归测试。

## Migration Plan

无需数据库迁移。发布后旧数据库直接使用新增仓库查询；回滚只需移除 AppBar 搜索入口和 `search` 方法，既有数据不受影响。

## Open Questions

- 拼音搜索、繁简归一和更高质量的中文分词留待后续独立变更。
