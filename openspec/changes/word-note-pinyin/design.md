## Context

当前 `WordNote` 统一承载 L2 自动词语解释和用户选词解释，字段包含 term、explain、来源、行号和选区位置。AI 返回的词语信息会被解析后写入 notebook JSON，并在赏析列表或原文解释面板中展示。旧条目没有 pinyin 字段，因此模型和 UI 必须按可选字段兼容。

## Goals / Non-Goals

**Goals:**

- 新生成的词语解释尽量返回标准汉语拼音及声调。
- 自动词注和用户选词使用同一字段、同一展示格式。
- 旧缓存和模型遗漏拼音时不崩溃、不显示伪造读音。

**Non-Goals:**

- 不在本地根据汉字推断多音字读音。
- 不把拼音作为诗词检索字段。

## Decisions

### 1. 拼音由 LLM 返回，字段可选

在 `WordNote` 增加 `pinyin` 字符串，解析时缺失或空值默认为空；生成 Prompt 要求使用带声调符号的汉语拼音，词语内部用空格分隔。由于中文多音字必须结合语境判断，首版不使用简单的本地字符映射替代模型结果。

备选方案：引入本地拼音库。它能减少一次模型输出依赖，但增加包体和多音字语境判断复杂度，且与用户自配模型的现有生成流程不一致，暂不采用。

### 2. 展示层按“词语（拼音）”显示

赏析列表显示 `term（pinyin）：explain`；解释面板将词语作为主标题、拼音作为独立的辅助文本，再显示解释。pinyin 为空时只显示 term 和 explain，不显示“拼音未提供”这类噪声，保证旧缓存视觉兼容。

### 3. 不把拼音缺失视为解析失败

拼音是学习增强字段，不影响 term/explain 的核心解释协议。模型返回合法词语和解释但遗漏 pinyin 时仍保存结果；下次用户主动重新生成即可补全。这样不会让兼容供应商因新增字段导致整次赏析失败。

## Risks / Trade-offs

- [模型拼音带有声调数字、格式说明或大小写不统一] → Prompt 规定带声调符号且只返回字段；UI 原样展示非空结果，不自行改写可能改变读音的内容。
- [多音字读音判断错误] → 继续沿用 AI 赏析的“仅供参考”定位，不编造本地权威读音；后续可增加人工编辑拼音能力。
- [旧缓存没有拼音] → 可选字段默认空，旧 JSON 无需迁移。

## Migration Plan

无需数据库迁移。新生成的 `word_notes` 和 `word_note` JSON 会写入 `pinyin`；旧条目读取时默认为空。回滚代码后新增字段会被宽容忽略，不影响旧逻辑。

## Open Questions

- 拼音是否需要支持用户在编辑器中单独修订，沿用现有整条解释编辑能力，后续再细化。
