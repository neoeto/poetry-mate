## Context

当前应用的 `ChatSheet` 只能围绕已经打开的一首本地诗词追问；`ReaderPage`、`AnnotationService` 和 `NotebookRepository` 也都默认诗词已经存在于本地 `poems` 表。用户希望先用 AI 描述需求，再从 AI 已知的既有中文文学作品中找到本地库之外的一首作品。

这不是 AI 作诗：AI 必须被要求返回可识别的既有作品，不能仿写、续写或把模型临时创作的文本当作名作。作品范围也不能继续假定只有 `shi/ci`，需要容纳《诗经》、古文、近现代诗歌等文本。

本变更同时存在两个阅读生命周期：

```text
持久化作品：AI 寻诗 → 用户保存 → 扩展诗词库 → 普通阅读/注本流程
临时作品：  AI 寻诗 → 仅本次阅读/解析 → 离开页面后全部丢弃
```

## Goals / Non-Goals

**Goals:**

- 增加独立的 AI 寻诗多轮对话，并以结构化结果呈现一首 AI 认为已经存在的作品。
- 让外部作品可以复用现有阅读页和 L1/L2/L3 AI 解析能力。
- 将用户保存的作品放入独立的本地“扩展诗词库”，不改变公共/ETL 诗库。
- 在保存前识别内置库、导入库和扩展库中的重复作品。
- 支持真正的临时阅读模式：临时作品、解析结果和对话记录均不写入任何持久化存储。
- 对作者、年代、出处和原文的未知或不确定状态进行显式标记。

**Non-Goals:**

- AI 原创作诗、仿写、续写、改写或写诗辅助。
- 接入网页搜索、第三方文学数据库或自有服务端检索接口。
- 将外部作品并入原有 ETL 数据包或服务端 R2。
- 承诺验证作品的版权、作者归属、年代、出处或文本版本。
- 在本变更中实现扩展诗词库的云同步、分享或跨设备备份。

## Decisions

### 1. 将功能定义为“AI 寻诗”，而不是“AI 生成诗词”

AI 寻诗会话使用 system prompt 明确要求：只能返回模型认为已有的作品；不能原创、仿写或用不确定内容冒充名作。模型无法给出可信作品时返回 `not_found`，UI 展示未找到，而不是把自由文本直接当作诗词保存。

最终响应使用 JSON 对象，核心字段包括：

- `status`: `found` 或 `not_found`；
- `title`、`author`、`period`、`genre`；
- `paragraphs`，可选 `preface`、`rhythmic`；
- `source`、`source_confidence`；
- 可选的简短推荐理由。

模型返回的会话消息只在内存中保留。作品是否持久化由用户在结果页明确选择，而不是由 AI 调用自动决定。

**考虑过的替代方案：**

- 直接让模型输出 Markdown：实现简单，但难以可靠提取标题、正文、出处并执行去重，因此不采用。
- 由服务端调用公共搜索 API：能改善来源核验，但违反 BYOK、服务端不代理 LLM/用户数据的架构，也引入版权和运维边界，因此不采用。

### 2. 扩展作品使用独立表和仓库，阅读层继续复用 `Poem`

新增本地 `extended_poems` 表保存用户明确加入的作品，至少包含：独立 ID、去重指纹、标题、作者、时期、体裁、正文段落、序文/词牌、出处、可信度和创建时间。原有 `poems` 表仍只代表内置/导入公共诗库，不新增外部作品到其中。

领域层新增扩展作品模型，并提供到阅读所需 `Poem` 形态的适配器。已有 `Poem` 阅读组件继续接收统一的可读文本字段；外部元数据显示通过扩展作品上下文或可选元数据字段提供。未知字段使用“作者不详”“时期不详”等安全展示值，同时保留原始未知/不确定状态用于提示。

扩展库拥有独立页面和入口，列表、打开和再次阅读都经由扩展作品仓库；注本列表在解析关联作品时同时解析公共库和扩展库。

**考虑过的替代方案：**

- 直接给 `poems` 表增加 `is_external`：会把公共数据和用户资产混在一起，使 ETL 重灌、分类和数据归属复杂，因此不采用。
- 只把作品放进 `notebook_entries`：阅读路由无法稳定加载正文，也无法形成独立扩展诗词库，因此不采用。

### 3. 用与公共诗词 ID 一致的正文指纹做只读去重

保存前为 AI 结果计算 `contentFingerprint`：对简体正文/序文执行与 `poem-id` 契约一致的 NFC 归一化、去标点、去空白，并保留段落边界后计算 SHA-256 前 32 位。该值只用于候选去重，不替换、不重写公共数据包中的 ID。

- 公共库记录的 ID 已经由同一正文契约生成，因此候选指纹与公共记录 ID 相等时视为已存在。
- 扩展库单独建立 `fingerprint` 唯一索引，防止同一作品重复保存。
- 去重以正文/序文为主，不依赖 AI 返回的作者或标题；这样作者归属差异不会制造副本。
- 若候选与公共库重复，优先打开公共库作品并提示“本地诗库已有”；不创建扩展记录。

扩展作品 ID 使用独立命名空间，不能因为与公共作品有相同指纹而让两个表共享可冲突的路由 ID。公共库后续导入同一作品时，扩展库不得在用户界面再次展示副本；导入完成后由扩展仓库清理或隐藏与公共库指纹相同的记录。

**考虑过的替代方案：**

- 只比较标题和作者：容易受异名、作者归属和字段缺失影响，无法识别同正文作品。
- 只做全文字符串比较：无法容忍繁简、标点和空白差异，且与现有公共 ID 规则不一致。

### 4. 通过阅读上下文区分持久化和临时解析

现有 L1/L2/L3 服务默认命中或写入 `NotebookRepository`。本变更增加显式的阅读持久化上下文：

- `persistent`：公共作品和已保存扩展作品，沿用现有注本缓存、编辑保护、重新生成确认和对话落库逻辑。
- `transient`：临时作品只使用当前阅读会话的内存缓存；L1、L2、选词解释和 L3 对话不得读取或写入 `notebook_entries`，不得显示“编辑注本”入口。关闭阅读页/会话后释放内存。

临时模式仍允许在当前页面内重复打开已生成的内容而不重复请求；这只是会话缓存，不构成持久化。用户在结果页选择保存时只保存作品本身；此前临时会话中的解析和对话不迁移，保存后的后续打开才进入正常持久化流程。

**考虑过的替代方案：**

- 临时模式也写注本、离开时删除：存在崩溃、中断或删除失败导致用户数据残留的风险，不满足“都不保存”。
- 为临时作品使用一个特殊 poem ID 继续写现有注本：仍会产生持久化数据，也可能与真实作品 ID 冲突，因此不采用。

### 5. 复用阅读页面，但增加外部来源提示和临时路由

保存作品通过扩展库路由打开，临时作品通过内存中的阅读上下文打开；两者最终都渲染现有的一句一行正文、白文模式、选词菜单和 L1/L2/L3 控件。外部作品页在标题/元数据附近增加“AI 补充作品”及来源可信度提示。

`genre` 使用可扩展字符串，不再假定只有 `shi/ci`。阅读排版仍按段落显示；不是词的外部作品不强行套用词牌逻辑。作者、时期、出处未知时显示对应的待核提示，而不是空白或虚构信息。

### 6. 外部作品的赏析必须继承事实护栏

对外部作品做 L1/L2/L3 解析时，将正文视为唯一可靠文本；AI 寻诗响应中的作者、年代、出处和推荐理由是未核验元数据。整篇赏析不得根据这些字段编造背景，无法确认时背景留空并标记不确定。临时和持久化两种模式只影响保存，不降低事实护栏。

### 7. 数据只落 APP 本地，服务端无变更

扩展作品和持久化解析只写 APP 本地 SQLite。AI 寻诗、临时会话、临时解析和 API Key 仍通过用户配置的 LLM 直连，不经过 Worker/R2；服务端、ETL 和公共数据包不新增字段或接口。

## Risks / Trade-offs

- **[Risk] LLM 可能把原创文本或错误版本冒充既有作品。** → 强制结构化响应、明确禁止原创、要求出处/可信度字段；UI 显示“AI 补充/信息待核”，不承诺自动核验；解析背景默认按不确定处理。
- **[Risk] 模型返回 JSON 不完整或字段类型错误。** → 复用现有 JSON 围栏剥离、重试和坏响应降级机制；只有通过正文非空、段落合法和 `status=found` 校验的结果才能进入预览或保存。
- **[Risk] 去重规范与 ETL ID 不一致会产生副本。** → 在 APP 中实现与 `poem-id` 规范一致的纯指纹函数，并用繁简、标点、空白及段落边界测试覆盖；指纹只作去重，不修改现有 ID。
- **[Risk] 现有注解 UI 默认显示编辑/缓存入口，临时模式可能误写数据。** → 将持久化上下文作为显式参数贯穿阅读页和注解服务；临时分支禁止访问仓库，并增加数据库无写入断言测试。
- **[Risk] 扩展库作品数量增长后与公共库解析关联成本上升。** → 扩展仓库为指纹建立索引，列表和按 ID 查询保持独立；公共库查询仍走原仓库，只有需要展示时做明确的来源解析。
- **[Trade-off] 临时模式关闭页面后丢失解析结果。** → 这是用户选择“一次性查看”的明确语义；保存按钮只保存作品，避免未经明确同意保存会话和注解。
- **[Trade-off] 不接入外部检索意味着来源核验能力有限。** → 保持 local-first、BYOK 和隐私边界；通过来源和可信度提示管理预期，而不是伪装成权威数据库。

## Migration Plan

1. 增加 `extended_poems` 本地表和必要索引，数据库 schema 版本递增；升级只创建新表，不改写既有 `poems`、`favorites` 或 `notebook_entries` 数据。
2. 增加扩展作品仓库、指纹工具、作品解析模型和 Riverpod provider；更新作品解析入口，使公共作品和扩展作品都能被注本页面解析。
3. 增加 AI 寻诗会话和结果页；结果先经过结构校验与公共/扩展库去重，再提供“加入扩展诗词库”和“仅本次查看”。
4. 给阅读/注解链路增加 persistent/transient 上下文；为临时模式提供内存缓存并隐藏注本编辑入口。
5. 增加路由、扩展库页面、来源提示和相关单元/UI/迁移测试。
6. 回滚时可以停止展示新入口并继续使用已有功能；已完成的 SQLite migration 不降级回滚，未使用的 `extended_poems` 表保留但不参与公共库查询。服务端无需发布或回滚。

## Open Questions

- 默认入口可同时放在“今日”页的 AI 卡片和“我的”页的功能列表中，具体视觉位置可在 UI 实现时按现有导航密度确定，不影响数据和路由契约。
- 当 AI 返回作品与公共库重复时，本设计默认直接复用公共库版本；若用户希望查看 AI 返回的异文，需另行定义“版本/异文”能力，不在本变更中隐式保存。
